Phase 1 Implementation Plan — replay-core: Trace Store, Cuts/Slices, Git Snapshot Store

Produced under the feature-pr-pipeline skill (Stage 1, writing-plans). For agentic workers: REQUIRED SUB-SKILL — subagent-driven-development (fresh implementer + task reviewer per task), test-driven-development inside each task. Steps use checkbox syntax for tracking.

Goal: Build the persistent half of replay-core — an append-only, content-addressed trace store (F2) holding records under the Phase 0 identity law, immutable Cut/Slice addressing with projections and epoch slicing over it (F3), and a Git-backed dual-tree snapshot store (F4) — so a synthetic run's records, slices, and snapshots round-trip end-to-end byte-identical, with GC-survival and concurrent-append evidence, discharging the Phase 1 gate.

Architecture: Three new packages under internal/, layered strictly downward: internal/snapshot and internal/slice consume internal/store; internal/store consumes only Phase 0's internal/canonical and internal/record. The trace store is one SQLite file whose schema mirrors the design evidence (records, path entries, causal edges, append intents, frontiers, per-owner ordinals, witness bodies); identity is enforced in the database itself by a CHECK (record_id = digest) constraint and re-validated on every read. The snapshot store is a bare Git repository driven through plumbing commands; snapshots are dual-tree commits (workspace/ + meta/) and worlds/scopes are refs. The two stores are separate; the only coupling is a one-way citation — a milestone record in the trace store names a snapshot commit.

Tech Stack: Go 1.27 (module github.com/pratik-saptarshi/replay-core); database/sql with the CGO SQLite driver github.com/mattn/go-sqlite3 (the module's first external dependency — Decision 1); the git binary's plumbing commands via os/exec (git 2.43.0 present in this environment — Decision 2); Phase 0 packages internal/canonical and internal/record, unmodified.

Spec: docs/replay-semantics.html (in-repo normative spec, especially §4 fork-at-cut, §5 projection-only revert, §7 memory charter); the ratified roadmap and its Phase 1 feature specs and acceptance criteria (AEP goal workspace, 2026-11-18: roadmap matrix v1.3, feature specs §1–§3, acceptance criteria AC-F2-1…AC-F4-5 and AC-GATE-1). Decisions (made by this plan, for the owner's plan review)

Decision 1 — Storage engine for F2: SQLite via the CGO driver github.com/mattn/go-sqlite3. The alternatives were weighed against the acceptance criteria as written, not against preference:

  • Non-SQL store (custom file format / embedded KV) — rejected on AC fidelity. AC-F2-3's check is, verbatim, a “direct INSERT with a deliberately mismatched record_id” asserting a constraint violation, and its build-phase remediation demands a mutation sweep over insert paths “including raw-SQL bypass attempts”. A store with no SQL surface cannot discharge that criterion as written; choosing it would mean silently rewriting a ratified AC. The design evidence also describes the store as one SQLite file with BEGIN IMMEDIATE atomicity and the CHECK constraint — the criteria and the evidence agree.
  • Pure-Go SQLite (modernc.org/sqlite) — viable, not chosen. It is genuine SQLite (transpiled) and keeps CGO off, but it is a very large dependency tree and its transpiled amalgamation is compile-time memory-hungry; in this sandbox (~1.5 GiB effective memory, sequential builds) a cold build risks becoming the phase's pacing item. If a future platform forbids CGO, this is the fallback and the store's SQL surface is written to be driver-portable (standard database/sql, no driver-specific SQL beyond pragmas).
  • CGO driver (mattn/go-sqlite3) — chosen. The canonical driver over the SQLite amalgamation: CHECK constraints, BEGIN IMMEDIATE, and WAL behave exactly as the evidence describes. gcc is present in this environment (verified 2026-11-18) and the Go toolchain here already builds CGO packages.

Dependency-policy consequence, stated plainly: Phase 0 shipped with zero dependencies. This plan adds the module's first require (Task 1) and makes every build a CGO build (CGO_ENABLED=1, gcc required). That is a visible change to the project's build contract, taken because the ratified criteria presuppose a real SQL store. No other third-party dependency is added in Phase 1. One further consequence rides with the CGO choice: release binaries for non-host targets will each need a C cross-toolchain for that target, and any future CI host needs gcc — a deferred cost, since the repo has no CI yet.

Decision 2 — Git access for F4: shell out to the git binary's plumbing commands. The snapshot design is refs-and-trees shaped (bare repository, refs/vcscore/… layout, dual-tree commits, incremental tree assembly), and plumbing (hash-object, update-index, write-tree, commit-tree, update-ref, for-each-ref, count-objects) is the stable interface built for exactly this. A pure-Go Git library would be a second large dependency whose tree-building APIs do not map cleanly onto the incremental dual-tree build, and its memory would be spent inside the Go process, under the sandbox ceiling; the subprocess keeps Git's memory in Git's process. Cost: a runtime dependency on the git binary. An explicit capability probe in snapshot.Open (Task 13) exercises one plumbing verb and fails loudly with a named error if it is unavailable, which is also the empirical spike the feature spec asked this plan to run; the probe does not by itself discharge the runtime-dependency risk — the remaining verbs are ancient, stable plumbing, and any failure among them surfaces in Task 13's tests rather than in production use. Committer identity is pinned per-invocation (-c user.name=replay-core -c user.email=replay-core@localhost) so snapshot commits never depend on host Git configuration.

Decision 3 — File layout (following the existing internal/ pattern). New packages: internal/store (F2), internal/slice (F3), internal/snapshot (F4). The Phase 1 gate demonstration joins internal/conformance as a test file, mirroring Phase 0, and scripts/check-phase1.sh mirrors scripts/check-phase0.sh. No Phase 0 package is modified. Reserved schema constants (replaycore.milestone.v1, replaycore.cut.v1, replaycore.abandon.v1) live in internal/store — the lowest layer — so the store's GC can recognize cut and milestone records as retention roots without an import cycle (slice and snapshot import store, never the reverse).

Decision 4 — smaller calls the specs left open, pinned here. (a) The spec's AppendFact(owner_path, body, caused_by[], mode, schema_ref) elides the witness the Phase 0 law requires of every non-root record; plan drafts therefore carry witness material explicitly (RecordDraft.WitnessBody + WitnessSchemaRef), and the store computes the witness digest. “Witness body” throughout this plan means the witness fields object — the value record.ValidateWitnessBody and record.WitnessBodyDigest consume (Phase 0's record.RootWitnessBody() returns those fields wrapped in the witness object; the fields are its body field). Store-minted records (cuts, milestones, abandon facts) carry the root witness fields as their witness — deterministic, already computed in Phase 0, and lawful (a valid witness body, digest sha256:22e3bf15…85721130). (b) Milestone and cut records are exempt from mode filtering (resolving the F3 spec's open question): a mode filter that could drop a boundary marker would silently move epoch boundaries; the purity law in Task 8 is stated over this one well-defined filter function. (c) GC collects only records unreachable — via caused_by closure — from the retention roots (every frontier, every published cut, every milestone); this is a storage operation under AC-F2-7's survival guarantee, distinct from revert, which remains projection-only (spec §5) and deletes nothing. (d) The spec's CiteSnapshot(milestone_record, commit_id) is realized as body construction before append (store.MilestoneBody + store.AppendMilestone), because an append-only store cannot edit a record after the fact; the citation lives in the milestone body, per the F4 spec's normative placement. The body constructor lives in internal/store (milestone.go, beside AppendMilestone): the store is the lowest layer and must never import snapshot, so the single construction site cannot sit in the snapshot package — internal/snapshot/cite.go consumes store.MilestoneBody instead (Task 16).

Global Constraints

  • Record model (normative, as built in Phase 0): a record is {body, caused_by, kind:"record", mode, schema_ref, witness}; mode is exactly capture or declaration (record.ModeCapture / record.ModeDeclaration); a witness body has exactly the eight fields active_binding_refs, actor_ref, authority_refs, containment, provenance_policy_refs, semantic_environment_refs, substrate_ref, visibility_policy_refs. The store adds no fields to the record itself.
  • Identity law: record_id == digest always, under the canonical-digest law with prefix replaycore.kernel.canonical.v1; digests are sha256:<lowercase hex> of the prefix-tagged canonical bytes, computed only through internal/canonical and internal/record (record.RecordDigest, record.WitnessBodyDigest, record.RecordInput). Ground truths: root witness body digest sha256:22e3bf15914b5007dea08a1079d1542470a369bcbed067687f345e7e85721130; root witness record ID sha256:0b67497cb4c0f2ed954b7988ecc321b481e7d173c4fc201adeb86591b2fd6310 (computed by record.RootWitnessRecordID(), never hardcoded in implementation code).
  • Corpus discipline: testdata/corpus is frozen Phase 0 ground truth. Phase 1 adds no corpus cases, modifies none, and scripts/check-phase0.sh must stay green at every commit.
  • Append-only: no API deletes or rewrites a record. Revert is projection-only (spec §5). The single exception is garbage collection under Decision 4(c), which may remove only records unreachable from the retention roots and must never remove a record a frontier, published cut, or milestone can reach.
  • Mode-filter law: causal closure first, mode filter second — a filtered Slice is the filter applied to the full causally closed Slice, never a closure computed over the filtered subset. Records with schema_ref replaycore.milestone.v1 or replaycore.cut.v1 are exempt from mode filtering (Decision 4(b)).
  • Reserved schema_refs: replaycore.milestone.v1 (body {task_id, snapshot_ref}), replaycore.cut.v1 (body {owner_path, through_fact_id, through_owner_ordinal}), replaycore.abandon.v1 (body {abandoned}), alongside Phase 0's kernel.witness.root.v1. Owner paths beginning replaycore. are reserved; AppendBatch rejects them (the root witness record lives on the reserved path replaycore.system).
  • Task boundaries are claimed, not enforced (directive X1): the store accepts a milestone naming any task id and exposes no API that validates, mints, or rejects task boundaries (AC-F2-9). Epochs are per owner path only; no Phase 1 API accepts a set of per-path cuts as an epoch (AC-F3-7).
  • Dependencies: exactly one new module requirement in Phase 1 — github.com/mattn/go-sqlite3 v1.14.53 (Decision 1; the current v1.14.x patch, verified against the module proxy at plan time). Everything else is stdlib plus Phase 0 packages. Builds are CGO builds: CGO_ENABLED=1.
  • Environment: this sandbox has ~1.5 GiB effective memory. Verification commands run package tests sequentially (one package per go test invocation in gate scripts), with GOTMPDIR=$HOME/.gotmp and PATH including $HOME/sdk/go/bin. Fixtures are generated in-test under t.TempDir(); no binary fixtures are committed.
  • Hygiene: this repo is public. Plan and code cite the design evidence by the roadmap's aliases (“the features plan”, findings sections, “the reference suite/design”) only.

Review Focus

The five input classes / failure modes the spec implies but the acceptance criteria do not directly exercise, most likely to bite first. Each is pinned to its owning task with a test in that task's steps.

  1. Unclean shutdown and reopen. A lane process killed between runs leaves a WAL behind; on reopen the store must recover with every committed record intact, frontiers consistent, and no ordinal reuse. AC-F2-1 covers a kill during a batch; nothing covers reopen-after-crash as a routine operation. → Task 1, TestStoreReopenAfterUncleanClose.
  2. Hostile causal citations in a draft. A draft that cites a nonexistent record, cites itself, or forms a cycle inside its own batch would corrupt closure computation (Task 7) or hang it. A reasonable caller expects rejection at append time, not a poisoned store. → Task 1, TestAppendBatchRejectsUnknownAndSelfCitations.
  3. Degenerate appends. An empty batch, an empty intent id, or an empty owner path are the inputs every caller eventually produces by accident; a silent success would mint receipts for nothing or file records under no path. → Task 2, TestAppendBatchRejectsDegenerateInputs.
  4. Workspace entries that are not plain files. A snapshot walk that follows a symlink snapshots bytes outside the workspace (a correctness and containment failure); an unreadable file silently skipped produces a snapshot that claims completeness it does not have. Expected: symlinks are stored as links, never followed; unreadable entries fail the snapshot loudly, naming the path. → Task 13, TestSnapshotStoresSymlinksAsLinks and TestSnapshotFailsOnUnreadableFile.
  5. Very deep causal chains. Real traces are long; a recursive closure over a 10,000-record chain overflows the goroutine stack or turns resolution quadratic. Expected: closure is iterative and resolution of a deep cut completes with the full prefix. → Task 7, TestResolveCutDeepChain.
