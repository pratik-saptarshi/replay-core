Phase 2 Implementation Plan — replay-core: Carrier Protocol, Settlement

Produced under the feature-pr-pipeline skill (Stage 1, writing-plans). For agentic workers: REQUIRED SUB-SKILL — subagent-driven-development (fresh implementer + task reviewer per task), test-driven-development inside each task. Steps use checkbox syntax for tracking.

Goal: Build the workspace half of replay-core — a carrier protocol with probed, honestly-degrading drivers (F5) that materialize a snapshot's workspace tree as a writable layer without ever touching the base, and fail-closed settlement (F6) over those layers: fast-forward-only select, path-disjoint apply, archive-on-discard, consume-once outputs, journaled materialization — so a real repository workspace can be forked, settled with disjoint outputs, and refused with overlapping ones, discharging the Phase 2 gate.

Architecture: Two new packages under internal/, layered strictly downward. internal/settle (F6) consumes internal/carrier (F5), internal/snapshot (F4), and internal/store (F2). internal/carrier consumes nothing internal — it is a directory-level protocol (probe, select, materialize, remove) that never sees Git or the trace; extracting a snapshot commit's workspace/ subtree into a base directory is the snapshot package's job, and settlement orchestrates the two. The snapshot package gains a small scope/tree surface (scope head reads, compare-and-swap scope advance, scope archiving, workspace-tree reads and extraction) and the store gains settlement-fact constructors beside its existing minting pattern; no Phase 0/1 package's existing public contract changes. Settlement correctness never depends on the carrier (the features plan §7: journal + verify-after make correctness carrier-independent).

Tech Stack: Go 1.27 (module github.com/pratik-saptarshi/replay-core); no new module dependencies in Phase 2 (Decision 2) — carrier mechanics use the standard library's syscall package on Linux (overlay mount, FICLONE ioctl); Git access remains the git binary's plumbing via internal/snapshot (Phase 1 Decision 2); the CGO SQLite driver from Phase 1 is untouched.

Spec: docs/replay-semantics.html (in-repo normative spec, especially §5 projection-only revert and §8 — “the settlement gates apply before anything touches a real tree: fail-closed settlement (fast-forward-only select, path-disjoint apply, archive-on-discard)”); the ratified roadmap and its Phase 2 feature specs and acceptance criteria (AEP goal workspace, 2026-11-18: roadmap matrix v1.3, feature specs §4–§5, acceptance criteria AC-F5-1…AC-F5-10 and AC-F6-1…AC-F6-7, host baseline 2026-11-18 §§1–4). Phase scope, verbatim from the features plan §6: Phase 2 is “F5+F6: carriers (overlayfs + reflink), journaled settlement”. This plan refines the roadmap's Phase 2 decomposition (T-F5-1…5, T-F6-1…4, T-GATE-P2) into executable tasks without re-cutting it: plan tasks keep roadmap task IDs, in roadmap dependency order. The roadmap's Phase 2 header counts “Tasks: 10 (matrix)” against nine work packages; the tenth is the gate task, exactly as Phase 1's 17 counted sixteen work packages plus T-GATE-P1.

Decisions (made by this plan, for the owner's plan review)

Decision 1 — File layout (following the existing internal/ pattern). New packages: internal/carrier (F5), internal/settle (F6). The carrier is deliberately Git-agnostic and store-agnostic: it materializes a layer from a base directory plus a base identity, so its protocol conformance is testable without either store, and a carrier bug cannot reach a real tree — only settlement writes to real trees, and only at its verbs' commit points (AC-F6-7). Additions to existing packages are confined to two files' worth of surface, each justified by a consumer in this phase: internal/snapshot gains scope-head/CAS/archive operations and workspace-tree reads/extraction (Task 6 — the Phase 1 Task 16 cite.go precedent: cross-package needs land as small, guarded additions in the owning package), and internal/store gains settlement-fact constructors (Decision 4). The Phase 2 gate demonstration joins internal/conformance as a test file, mirroring Phases 0–1, and scripts/check-phase2.sh mirrors scripts/check-phase1.sh. Layering, machine-checked by the build: settle → {carrier, snapshot, store, canonical}; carrier → stdlib only; snapshot and store never import settle or carrier.

Decision 2 — No new module dependencies; carrier mechanics via the standard library. The kernel-overlay mount and the FICLONE ioctl are both reachable from the standard library's syscall package on Linux (syscall.Mount, syscall.Syscall(syscall.SYS_IOCTL, …)), in Linux-tagged files with a small non-Linux fallback that reports each driver unavailable with its reason. The module therefore keeps exactly one requirement (github.com/mattn/go-sqlite3, Phase 1 Decision 1). The one dependency this decision refuses is a FUSE library — see Decision 5.

Decision 3 — One scope identity across both stores; fork provenance is settle-side operational state. A settlement scope is named once: the scope name is both the snapshot scope ref (refs/vcscore/scopes/<name>, matching the Phase 1 scope-name law ^[a-z0-9][a-z0-9-]*$) and the trace owner path its settlement facts are appended to. AC-F6-7's “the scope's tail” is then well-defined: the frontier of the owner path named by the scope. Fork provenance — parent scope, fork commit, base (workspace) tree — is recorded by settle.Fork in a sidecar file under the settle root (forks/<runScope>.json, canonical JSON, fsynced before the layer is handed out). It is operational state of the same kind as the journal (Decision 8(e)), not a trace fact: AC-F6-7 enumerates the settlement facts as the three verbs' records, and the plan does not add a fourth fact class on its own authority. Advancing a run line between fork and settlement (snapshotting the layer, moving the run scope's head) is the caller's composition of snapshot.Snapshot + snapshot.AdvanceScope; settle owns only the fork and the verbs.

Decision 4 — Settlement facts are reserved, store-minted records (the Phase 1 minting pattern). Three new schema refs — replaycore.settle-select.v1, replaycore.settle-apply.v1, replaycore.settle-discard.v1 — join the reserved set: AppendFact/AppendBatch reject them with ErrReservedSchemaRef, and their bodies are constructed and minted only by new constructors in internal/store (settle.go, beside mint.go), each minting with caused_by = the scope path's frontier at mint time and the root witness fields as witness (Decision 4(a) of the Phase 1 plan: the house convention for system-authored facts). This is the wave-2 (ADV-3) lesson applied prospectively: a fact class that other code will trust — consume-once enforcement and crash completion both read settlement facts as authority — is never appendable through the unguarded path. Each body carries the caller-supplied operation ID (op); consume-once and journal recovery key on (schema ref, run scope, op), never on wall-clock or ordering guesses. Body shapes, all flat: select {op, parent_scope, run_scope, parent_head, run_head}; apply {op, parent_scope, run_scope, fork_commit, result_commit, settled_paths}; discard {op, run_scope, head, archive_ref}.

Decision 5 — FUSE-overlay driver depth: protocol-registered and probe-honest; the mount itself is not built in Phase 2. The baseline is unambiguous: /dev/fuse is absent in this sandbox, so a FUSE driver cannot be exercised here at all — no test in this environment could distinguish a correct FUSE implementation from a plausible-looking one, and Phase 2's discipline is that unexercisable code does not ship as if proven. The driver therefore occupies its slot in the selection order with a real probe (it stats and opens /dev/fuse and records the outcome) and a materialize that refuses with the probe's recorded reason. AC-F5-9 is recorded host-deferred, not discharged (Decision 7); a future host with /dev/fuse present owes the mount implementation against the same isolation contract as AC-F5-5, and the probe will start reporting availability there only when the mount exists to back it — the probe and the mount land together or not at all. The alternative — a full FUSE implementation against a new third-party library, compile-verified only — was rejected: it adds the phase's only new dependency for code no test here can run.

Decision 6 — Issue #3 (intent path-scoping, and the parked identity question) does not interact with F5/F6; this plan neither uses nor settles it. Stated explicitly, as the issue's disposition (“deferred to Phase 2 design”) requires a Phase 2 answer: settlement appends are single, constructor-minted facts (Decision 4) — the verbs call the MintSettle* constructors, never AppendBatch, so the append_intents table, its key, and the AC-F2-2 contract are untouched, unread, and undepended-on by every task in this plan. Idempotency for settlement comes from the journal + op-ID scan (Task 8), not from the intent mechanism. The identity question is likewise untouched: settlement facts are ordinary content-addressed records under the existing law, and no task changes what a record's identity is computed from. Issue #3 therefore remains open for the owner's design call in parallel; if the owner settles it before or during Phase 2 execution, no task in this plan changes. (What F6 does rely on from Phase 1 is the wave-3 law as built: intent IDs are globally single-use and cross-path reuse is rejected — relied on only in the negative sense that nothing here needs the alternative.)

Decision 7 — Host-deferred criteria are built as drivers, never as gate evidence. Three Phase 2 criteria cannot be discharged in this sandbox (roadmap host-deferred register, baseline 2026-11-18 §§1–4): AC-F5-8 (kernel overlay on real workspaces — overlay mounts fail on this sandbox's btrfs workspace filesystem, mount exit 32 class), AC-F5-9 (FUSE overlay — /dev/fuse absent), AC-F5-10's extent-sharing clause (FICLONE refused, EPERM, on both filesystems here). Their drivers are built (Tasks 3–5) with honest probes, and the criteria are recorded not discharged wherever they are owned; no copy-carrier pass stands in for any of them, and the Phase 2 gate discharges through the copy carrier exactly as the roadmap's carrier note prescribes. Two partial discharges are available here and are claimed precisely: AC-F5-7 (kernel overlay at scratch grade on tmpfs) in Task 3, and AC-F5-10's no-silent-fallback clause (a failed clone is reported, never degraded to a byte copy) in Task 5 — the refusal path is exactly what this sandbox exercises.

Decision 8 — Smaller calls the specs left open, pinned here. (a) The selection order's third slot (AC-F5-1: “kernel overlay → FUSE overlay → clonefile → copy”) is occupied on Linux by the reflink driver: the features plan's F5 row lists “reflink/FICLONE (Linux, new)” and “APFS clonefile (macOS, later)” as the same slot's platform occupants, and the roadmap's per-carrier table names the third built driver “reflink”. The clonefile driver itself is out of Phase 2 scope (“later”). (b) A carrier layer's base identity is the snapshot workspace tree ID — a content identity, so the stale-layer wipe keyed on identity change (AC-F5-3) is exact, never heuristic: same identity, same content, by Git's own law. (c) A verb reads the parent's current state by snapshotting the parent directory (a “probe snapshot”): the ops chain is an append-only log, the probe commit moves no ref, and reusing Snapshot inherits its round-trip guard (a parent tree the snapshot store itself cannot record fails the verb before anything is written — the Phase 1 wave-5 law working as designed). (d) Select materializes the parent directory through the same materializer apply uses; Task 6 ships that materializer unjournaled and Task 8 rebuilds it on the journal without changing either verb's contract — the interim is stated in Task 6's Interfaces, not discovered later (the Phase 1 Task 7 honesty rule for intermediate states). (e) All settle operational state — fork sidecars, base extractions, layers, staging, journals — lives under one caller-supplied settle root (Context.Root); nothing in F5/F6 writes anywhere else except the parent directory at a verb's commit point and the two stores through their own APIs.

Global Constraints

  • Phase 0/1 law carries over, unchanged: the record model {body, caused_by, kind:"record", mode, schema_ref, witness}; identity record_id == digest under replaycore.kernel.canonical.v1; append-only (revert is projection-only, spec §5 — settlement is not revert: it moves refs and materializes trees, and deletes nothing but layers and its own operational state); the frozen corpus and scripts/check-phase0.sh / scripts/check-phase1.sh stay green at every commit.
  • Reserved schema_refs after this phase: Phase 0's kernel.witness.root.v1; Phase 1's replaycore.milestone.v1, replaycore.cut.v1, replaycore.abandon.v1; and this phase's replaycore.settle-select.v1, replaycore.settle-apply.v1, replaycore.settle-discard.v1 (Decision 4). Owner paths beginning replaycore. remain reserved; scope names (Decision 3) can never collide with them, as the scope-name law admits no dot.
  • Carrier honesty: selection is probed per call, per root — never cached across roots or calls (a verdict about one filesystem says nothing about another); a driver that cannot serve is recorded with its reason in the Selection, never silently replaced (AC-F5-1); a driver that was selected and then fails at materialize time fails the operation — fall-through happens only at selection time, never mid-operation. Settlement correctness is carrier-independent: no task may make a settlement property depend on which driver materialized the layer.
  • Graph compatibility (directive X1): a carrier materializes the workspace state a graph node cites, and carrier choice is invisible to the graph — the same milestone cut restores identically over any carrier, or the carrier has failed its contract. Settlement verbs append their own facts to the execution graph (AC-F6-7); a settled epoch is visible as graph structure.
  • Eval levels (ratified interpretation): the roadmap's L2 minimum applies to gate evidence only. The Phase 2 gate-evidence criteria are AC-F5-6, AC-F6-1, AC-F6-2, AC-F6-3, AC-F6-4; they are discharged at gate-proof level by their owning tasks and re-discharged in assembled form by Task 10. All other criteria are discharged at their matrix levels (integration, live-probe, unit) and no task inflates or deflates a level.
  • Host-deferred honesty: AC-F5-8, AC-F5-9, and AC-F5-10's extent-sharing clause are not discharged by this phase in this sandbox (Decision 7). Any test, comment, or report that touches them must say so in those words; a probe that reports a driver unavailable is the honest discharge of the probe's own contract, not of the driver's criterion.
  • Dependencies: no new module requirements in Phase 2 (Decision 2). Builds remain CGO builds (CGO_ENABLED=1, Phase 1 Decision 1). Linux-specific carrier files carry the _linux.go suffix; the package must still compile on other platforms, with every platform-bound driver reporting unavailable with a reason.
  • Environment: this sandbox has ~1.5 GiB effective memory. Verification commands run package tests sequentially (one package per go test invocation in gate scripts), with GOTMPDIR=$HOME/.gotmp and PATH including $HOME/sdk/go/bin. Fixtures are generated in-test under t.TempDir(); no binary fixtures are committed. Sandbox filesystem facts the tests rely on (baseline 2026-11-18, re-verified at Phase 1 close): the workspace filesystem is btrfs (overlay mounts fail, FICLONE refused); /tmp is a 512M ephemeral tmpfs (overlay mounts succeed, FICLONE refused); /dev/fuse is absent. Tests that depend on a filesystem kind must take their root from the filesystem they mean — os.TempDir() for tmpfs, a scratch dir under the working directory for btrfs — and say which they are doing.
  • Shape-assumption discipline (the Phase 1 lesson, baked in): Phase 1's six fix waves traced to fixtures that quietly assumed one shape — linear chains, quiescent runs, single handles, system-produced inputs, plain paths. Every Phase 2 task below names the shape assumptions its mechanism touches and carries at least one fixture that breaks each: branching graphs where a prefix and a closure differ, operations interleaved with competing writes, second handles and reopened stores, hostile inputs the system itself would never produce (special files, invalid-UTF-8 names, corrupt journals), and paths that are symlinks, aliases, or the wrong kind of filesystem object. A fixture is named for the assumption it breaks.
  • Hygiene: this repo is public. Plan and code cite the design evidence by the roadmap's aliases (“the features plan”, “the feature specs”, “the reference design”) only.

Review Focus

The five input classes / failure modes the specs imply but the acceptance criteria do not directly exercise, most likely to bite first. Each is pinned to its owning task with a test in that task's steps.

  • Selection verdicts that outlive their filesystem. A probe result cached at startup, or taken on the settle root's filesystem while layers live on another, reports overlay “available” for a btrfs workspace — AC-F5-2's failure witness in production clothes. Selection is per-call and per-root (Global Constraints), and Task 1 probes both filesystems live.
  • Disjointness escaping through an alias. The overlap check compares path strings; the parent tree can make two different strings the same file (a symlinked directory component, a . segment). A missed alias is AC-F6-3's failure witness with extra steps. → Task 7, TestApplyRefusesOverlapShapes (alias leg) and the TestDisjointCensus table.
  • Recovery trusting a corrupt journal. The journal is read back after a crash — possibly a crash that happened while writing the journal. A recovery that guesses from torn or hostile journal bytes can “restore” the parent to a state that never existed. → Task 8, TestRecoverRejectsCorruptJournal: canonical decode + shape validation, refusal without writes, journal left in place as evidence.
  • A fact minted for an act that did not complete. Settlement facts are authority for consume-once; a select fact minted before the ref actually moved makes a lie permanent and blocks the legitimate retry forever. The commit-point order is therefore fixed — materialize, verify, move the ref, mint the fact last — in Tasks 6–8, and Task 9's evidence test pins the ordering's observable consequences.
  • Wiping a directory the carrier did not create. Stale-layer wipe is a delete; pointed at a foreign directory (a caller's mistake, a reused layer root) it would destroy work the carrier has no claim on. → Task 2, TestMaterializeRefusesForeignDirectory: a markerless non-empty layer root is refused, never wiped; a corrupt marker is an error, never a guess.

type DriverID string

const (
    DriverKernelOverlay DriverID = "kernel-overlay"
    DriverFuseOverlay   DriverID = "fuse-overlay"
    DriverReflink       DriverID = "reflink"
    DriverCopy          DriverID = "copy"
)

// ProbeResult is one driver's probed verdict for one root.
type ProbeResult struct {
    Driver    DriverID
    Available bool
    Reason    string // why not, when Available is false; "" when available
}

// Selection is the selection record (AC-F5-1): the chosen driver
// and every probe that led to it, in selection order.
type Selection struct {
    Driver DriverID
    Probes []ProbeResult
}

// Select probes every registered driver against rootDir in the
// fixed order (kernel overlay, FUSE overlay, reflink, copy) and
// selects the first available. Copy is the floor: it is available
// on any writable root. An error is returned only when rootDir
// itself is unusable (missing, not a directory, unwritable) —
// never as a substitute for a recorded probe failure.
func Select(rootDir string) (Selection, error)

The driver registry is an ordered package-level list (var drivers []driver) of an unexported interface with three methods — probe(rootDir) ProbeResult, materialize(...), remove(...) (materialize/remove signatures arrive with the Layer type in Task 2; in this task every driver's materialize/remove returns a descriptive “driver not yet implemented” error). Package-internal tests may substitute the registry; the public Select always uses the real one. Probes are real from this task onward, because AC-F5-1/AC-F5-2 judge the record: the kernel-overlay probe creates a scratch overlay under the root (lower/upper/work/merged plus one lower file), mounts it, confirms the lower file is visible through the merged view, and unmounts; the reflink probe creates two scratch files and attempts one FICLONE; the FUSE probe opens /dev/fuse; each failure's Reason names the mechanism and the error class (e.g. the mount failure, the EPERM). Scratch is removed on every path. Selection is computed fresh on every call — no caching (Global Constraints). Interim honesty: until Tasks 2/3/5 land, Select can name a driver whose materialize does not exist yet; Task 1's tests therefore assert selection and records, never materialization, and the stub errors say exactly that.

// A Layer is one materialized workspace: Dir is the directory a
// run writes in. Bookkeeping never lives inside Dir (a marker in
// the writable tree would pollute the run's own delta).
type Layer struct {
    Dir    string
    BaseID string
    Driver DriverID
    // unexported: layer root, driver state (mounts, upper/work)
}

// Materialize builds (or reuses) the layer at layerRoot from
// baseDir, whose content identity is baseID (Decision 8(b): the
// snapshot workspace tree ID). Layout: layerRoot/layer.json is
// the marker ({base_id, driver}, canonical JSON); layerRoot/view
// is the writable directory (Layer.Dir).
func Materialize(sel Selection, baseDir, baseID, layerRoot string) (*Layer, error)

// Remove tears the layer down and deletes layerRoot entirely.
func (l *Layer) Remove() error

var ErrForeignLayerDir = errors.New("carrier: layer root exists and is not a carrier layer")

Materialize law: a layer root carrying a marker whose base_id and driver match the request is returned as-is (idempotent re-materialization — a second handle on the same layer, contents preserved). A marker naming a different base or driver means the base changed: the root is wiped and rebuilt, never merged (AC-F5-3). A non-empty layer root with no marker is refused with ErrForeignLayerDir — the wipe deletes only what the carrier created (Review Focus). A marker that fails to decode is a descriptive error, never a guess and never a wipe. Builds go to a staging sibling (view.building-*) renamed into place, with the marker written last; a staging remnant from a crashed build is removed by the next Materialize of the same root. The copy driver walks the base: directories recreated with their modes, regular files byte-copied with modes preserved, symlinks recreated as symlinks and never followed, and any other kind (FIFO, socket, device) refused with an error naming the path — a base the snapshot store could never have produced is hostile input, not a layer. Kernel-overlay and reflink materialize remain this plan's stated stubs until Tasks 3 and 5; Materialize with such a selection returns the stub's descriptive error.
