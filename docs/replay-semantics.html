Replay Semantics — replay-core

Status: normative spec for Phase 0; the statement Tasks 2–5 and all later phases argue from. Source of semantics: the features development plan for the replay capability (AEP goal workspace, 2026-11-18) §2 (and §3 for the charter and accounting rules). This page introduces no semantics beyond that plan. A reference design study found that the prior art's shipped kernel is an append-only record store that explicitly excludes replay, and its only replay implementation is a language-calculus prototype — so the semantics below are the ones replay-core defines and builds, at the provider boundary, for AEP's real workloads (orch-driven runs, SDD lanes, ESF executions).

1. Effect boundary

Replay is defined at the provider boundary, the only place nondeterminism enters a run. A run is a sequence of declared effects:

  • model calls,
  • tool executions,
  • filesystem settlements.

Everything inside the task program between effects is its own business; everything that crosses the boundary is an effect and is governed by the rules below. The shape is a request/completion pair — the program performs an effect request, the host completes it with an observation — generalized from a language-calculus prototype to a subprocess boundary.

2. Record by value

Each effect is recorded as a trace record carrying:

  • its request digest — the canonical-digest identity of the request (Phase 0 digest law), and
  • its full result payload, captured by value — for model calls, the exact request bytes and the exact response bytes.
Explicitly rejected: capture by digest only. A reference design's jailed path records a prompt digest and not the prompt itself, which makes its traces non-replayable — the exact model input cannot be re-derived from the trace. replay-core does not repeat that: a trace that cannot answer an effect from its own records is not a replayable trace.

3. Replay by digest match

Replay is the re-execution of the same task program in a fresh workspace fork, where every effect whose request digest matches the recording is answered from the trace instead of the world. The task program runs; when it reaches an effect, the replayer compares the effect's request digest against the recorded effect at that position:

  • Digest match — the recorded result payload is re-fed to the program; no live call is made.
  • First divergent effect — its digest does not match the recording. This effect marks the fork point; from there on, the run is live and its effects execute against the world (and are recorded as the new run's own trace).

4. Fork at a Cut

A Cut is an immutable read address over a trace. Fork-replay (counterfactual replay) starts from any Cut:

  • restore the workspace snapshot at that cut,
  • seed the effect cache from the trace prefix up to that cut,
  • optionally amend one recorded input,
  • and run.

Everything before the cut is inherited by reference; nothing is copied. Amending one input is the counterfactual: the run replays identically up to the amended effect and diverges live from there, under §3. This is the mechanism for re-running a failed or surprising run from the step before the failure with one input changed.

5. Projection-only revert

The trace store is append-only, and revert is projection-only, exactly as upstream defines it:

  • Abandon is a fact — abandoning a run appends an abandon fact to the trace; it edits nothing.
  • Effective history excludes abandoned runs — readers project the effective history from the facts, and abandoned runs are excluded from that projection.
  • Bytes are never deleted — there is no rollback and no deletion; selecting an earlier Cut is the only form of "going back".

6. Honesty rule

Replay guarantees identical inputs to the task program — not identical model behavior on live segments.
  • Clocks and RNG are recorded as effects when the program declares them; a declared clock or RNG read replays by digest match like any other effect.
  • Undeclared nondeterminism is a program bug — it is surfaced by digest mismatch at the next effect, not hidden by the replayer.
  • Consistent with the claims discipline of this phase: capability statements about replay cite the tests that prove them; measurement (for example, provider-reported cache-token counts) is recorded as measurement and never restated as a reuse guarantee.

7. Memory charter

replay-core is an execution store, not a memory system. NeuroStrata remains the memory of record. No second memory system is created.
  • At run close, replay-core inscribes pointers only — trace ids and cut addresses — into NeuroStrata.
  • The direction is one-way: replay-core writes pointers into NeuroStrata, never the reverse.
  • replay-core has no search or semantic APIs — retrieval over what a run meant is NeuroStrata's job; replay-core's job is what a run did, byte for byte.

8. Accounting note

  • A replayed effect that diverges is a live effect by definition — an effect that would re-fire a real-world action does so only because it diverged, and it is accounted as live.
  • All GitHub effects of replayed runs still pass through ghg, exactly as for a first run.
  • The settlement gates apply before anything touches a real tree: fail-closed settlement (fast-forward-only select, path-disjoint apply, archive-on-discard) governs the live segment of a replay just as it governs any run.

9. Settlement caller contract

Settlement — the settle layer's Fork, Select, Apply, Discard, and Recover — is single-caller: for a given settle Root and parent scope, at most one caller may be executing a settlement verb or a recovery at a time. Concurrent callers acting on the same parent scope, including separate processes, are outside the model.

This is a contract on the caller, not a property the system enforces: settlement does not detect, lock against, or prevent concurrent use. The reason is structural. A verb's entry recovery cannot distinguish a live operation from a crashed one — a journal on disk looks the same either way — so a second caller's entry recovery can roll back an in-flight operation's journal and staging, and two callers that both pass entry recovery can overwrite the same parent journal, either one's cleanup removing the other's recovery record. The parent ref's compare-and-swap protects the ref alone; it does not protect the filesystem mutations or the journal state, which have already occurred by the time the ref moves. A caller that needs settlement from more than one goroutine or process must serialize it externally: one caller per settle Root and parent scope at a time.
